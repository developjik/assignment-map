## 본질

AI 과제는 데모가 30분 만에 나오고, 그래서 변별이 안 된다. 심사위원이 실제로 보는 것은 모델이 느리거나 틀렸을 때의 설계다. 스트리밍을 붙이고 끝낸 지원자가 대부분이고, 통과하는 지원자는 실패 분류표와 평가 결과를 들고 온다.

승부처는 네 곳이다. 첫째, 키와 모델 호출이 서버 경계 안에 있는가. 클라이언트 번들에서 API 키가 나오는 순간 보안 과제로 전락한다. 둘째, 실패가 사용자 문구로 번역되는가. 타임아웃, 레이트리밋, 컨텐츠 필터, JSON 파싱 실패, 컨텍스트 초과는 서로 다른 문구와 다른 재시도 정책을 가져야 한다. 셋째, 프롬프트가 코드에 흩어져 있지 않고 버전이 붙어 있는가. 넷째, AI가 틀렸을 때 사용자가 알 수 있는가. 근거 없는 인용, 확신에 찬 거짓말을 화면에서 어떻게 걸러내는지가 사실상 당락을 가른다.

비용도 채점 대상이다. 요청당 토큰과 지연을 로그로 남기고, 사용자 한 명이 하루에 얼마를 쓰는지 한 줄로 계산해 두면 그 자체로 신뢰가 생긴다.

## AI 워크플로

### 1단계. 실패 분류표를 먼저 쓴다

모델, temperature, max tokens, 출력 스키마를 정하고, 실패 유형별로 사용자 문구와 재시도 정책을 표로 만든다. 표가 없으면 try/catch 하나로 모든 실패를 삼키게 되고, 사용자는 영원히 도는 스피너를 본다. 이 표는 그대로 코드의 에러 타입이 된다.

### 2단계. 서버 경계를 세우고 스트리밍을 붙인다

키는 서버 환경변수에만 둔다. 라우트 핸들러에서 업스트림 응답을 ReadableStream으로 감싸 SSE로 흘리고, 클라이언트는 누적 렌더와 AbortController로 중단을 처리한다. 중단 후 새 요청이 오면 이전 스트림을 확실히 닫는다. 401과 429는 화면마다 처리하지 말고 한 곳에서 처리한다.

### 3단계. 프롬프트를 코드 밖 자산으로 옮긴다

prompts/ 디렉터리에 시스템과 유저 프롬프트를 분리하고 변수 슬롯을 명시한다. 프롬프트 변경은 코드 변경과 같은 커밋 규칙으로 남긴다. few-shot 예시는 산문이 아니라 테스트 케이스로 고정해서, 프롬프트를 고쳤을 때 회귀를 바로 본다.

### 4단계. 골든셋으로 평가 루프를 돌린다

정상 5문항, 경계 5문항, 무관하거나 유해한 3문항으로 10~20개 골든셋을 만든다. 통과 기준(정확도, 형식 준수율, 평균 지연, 평균 토큰)을 정하고 실행 결과를 README 표로 남긴다. 실패 사례 두세 개를 그대로 적는 것이 중요하다. 다 통과했다고 쓰는 지원자는 아무것도 측정하지 않은 사람으로 읽힌다.

## 실전 프롬프트

### 실패 분류표 생성

```
아래 서비스의 LLM 호출 경로에서 발생할 수 있는 실패를 열거하고 표로 만들어라.
열: 실패 유형 / 감지 방법(에러 코드, 상태, 응답 내용) / 사용자에게 보일 문구 / 재시도 여부와 횟수 / 로그 필드
반드시 포함: 타임아웃, 429 레이트리밋, 5xx, 컨텐츠 필터 거부, 출력 JSON 스키마 불일치, 컨텍스트 길이 초과, 빈 응답.
재시도는 지수 백오프를 전제로 하고, 재시도하면 안 되는 유형은 그 이유를 한 줄로 적어라.
```

### 스트리밍 라우트 핸들러

```
Node 런타임 라우트 핸들러로 작성해라. 요구사항:
- 업스트림 스트림을 SSE(text/event-stream)로 중계하고, 클라이언트 연결이 끊기면 업스트림도 중단한다
- 첫 토큰까지의 시간과 총 토큰 사용량을 로그로 남긴다
- 429와 5xx는 지수 백오프 3회, 그 뒤에는 error 이벤트로 사용자 문구를 보낸다
- API 키는 process.env에서만 읽고, 응답이나 로그에 절대 남기지 않는다
- 타입 정의와 함께, 실패 경로 테스트 4개를 같이 작성한다
```

### 골든셋 평가 러너

```
골든셋(<파일 경로>)을 읽어 아래를 측정하는 스크립트를 작성해라.
1) 형식 준수율 (스키마 검증 통과 비율)
2) 정답률 (기대값과의 일치, 부분 일치는 partial로 집계)
3) 평균 지연과 p95, 평균 입출력 토큰
4) 실패 케이스의 원문 응답
결과를 콘솔 요약과 markdown 표로 출력하고, 기준 미달이면 exit 1로 끝낸다.
```

### 프롬프트 적대적 비평

```
이 시스템 프롬프트를 공격자 입장에서 비평해라.
- 프롬프트 인젝션으로 무시될 수 있는 문장
- 모델이 지어내도 검증되지 않는 주장
- 거절해야 하는 요청과 그 경계가 모호한 지점
- 출력 형식이 깨질 조건(긴 입력, 다국어, 표 요청)
각 항목마다 고친 문장을 그대로 제시해라.
```

## 탈락 방지

- [ ] 클라이언트 번들에 키 문자열 0건 (dist를 grep해서 sk- 로 시작하는 문자열이 없는지 확인)
- [ ] .env.example에는 변수 이름만 있고 값이 없다. .env는 커밋되지 않는다
- [ ] 스트림 중단(AbortController)과 재요청 시 이전 스트림 정리가 된다
- [ ] 429와 5xx는 지수 백오프 3회 뒤 사용자 문구로 끝난다 (무한 재시도 없음)
- [ ] JSON 출력은 스키마 검증 실패 시 1회 교정 요청, 그 뒤 폴백 응답
- [ ] 입력 길이 제한과 토큰 추정으로 컨텍스트 초과를 사전에 막는다
- [ ] 프롬프트가 컴포넌트에 하드코딩되지 않았다 (prompts 모듈과 버전 태그)
- [ ] 골든셋 결과(통과율, 실패 사례)가 README에 있다
- [ ] 모르면 모른다 규칙과 출처 없는 단정 금지가 시스템 프롬프트에 있다
- [ ] 요청별 usage 로그와 예상 월 비용 한 줄이 README에 있다
- [ ] 스트리밍 중 화면 이탈 시 요청이 남지 않는다 (네트워크 탭으로 확인)
