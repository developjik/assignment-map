## 본질

기능 목록을 다 구현해도 떨어지는 과제가 있고, 절반만 구현해도 통과하는 과제가 있다. 차이는 요구사항을 읽은 흔적과 깨졌을 때의 화면이다. 평가자는 30분 안에 코드를 훑고 5분 안에 앱을 클릭한다. 그 5분에서 빈 목록, 느린 응답, 잘못된 입력을 만나게 되고, 대부분의 지원자는 그 세 화면을 만들지 않는다.

기술적으로 승부가 갈리는 곳은 세 군데다. 첫째, 서버 상태와 클라이언트 상태를 섞지 않는 것. 목록은 서버 상태(캐시, 재요청, 낙관적 업데이트)이고 모달 열림과 필터는 클라이언트 상태다. 둘째, 데이터 계약을 먼저 정하는 것. 타입과 목 API가 있으면 UI 작업이 병렬로 풀리고, 없으면 화면마다 응답 모양을 상상하며 고친다. 셋째, 커밋 로그. 기능 하나가 커밋 하나로 남아 있으면 이 사람이 어떻게 생각했는지가 읽힌다.

디자인은 과제의 본론이 아니지만 감점 요소다. 라이브러리 기본 컴포넌트를 그대로 붙인 화면은 요구사항을 소화하지 않았다는 신호로 읽힌다. 색과 간격과 타이포를 토큰 몇 개로 고정하고, 상태별(로딩, 에러, 빈 목록, 성공)로 화면을 한 번씩 그려 두면 충분하다.

## AI 워크플로

### 1단계. 요구사항을 타입과 목 API로 굳힌다 (전체 시간의 10%)

코드를 먼저 시키지 않는다. 과제 명세를 그대로 붙이고 화면 목록, 엔티티, 상태 전이, 검증 규칙 네 표로 분해하게 한다. 그 표를 사람이 5분간 고친 뒤 표에서 TypeScript 타입과 MSW 핸들러를 생성한다. 이 단계에서 명세의 모호함(좋아요 취소가 가능한가, 목록 정렬 기준은 무엇인가)이 드러나고, 모호함은 README의 가정 항목으로 옮겨 적는다. 이것이 가장 큰 가점 포인트다.

### 2단계. 폴더와 스켈레톤은 한 번에 3파일 한도로

에이전트 모드에 폴더 규칙을 먼저 준다. src/app(라우팅, 프로바이더), src/features/<도메인>(api, hooks, components), src/shared(ui, lib). 한 번에 3~5개 파일까지만 생성하게 하고 매 응답마다 빌드한다. 10개 파일을 한 번에 뱉게 하면 타입이 서로 맞지 않는 코드가 나오고, 고치는 시간이 짜는 시간보다 길어진다.

### 3단계. 상태를 위에서 아래로 연결한다

서버 상태는 TanStack Query나 SWR로 모으고 queryKey를 도메인 단위로 고정한다. 클라이언트 상태는 URL 쿼리(필터, 페이지, 검색어)와 로컬 상태(모달, 입력 중 값)로만 나눈다. 전역 스토어는 정말 필요할 때만 쓴다. 각 훅마다 로딩, 에러, 빈 목록, 성공 네 경우를 화면에 붙이고 네 경우를 실제로 재현해 본다(네트워크 스로틀과 핸들러 500 반환).

### 4단계. 마감 90분은 테스트와 정리에 쓴다

기능 추가를 멈춘다. AI에게 실패 경로 테스트를 쓰게 하고(빈 배열, 401, 500, 타임아웃, 더블 서브밋, 아주 긴 문자열), 사람은 diff를 읽으며 AI가 남긴 군더더기를 지운다. 상태를 설정합니다 같은 설명형 주석, 쓰지 않는 import, any, 중복 컴포넌트. 마지막 20분은 README다. 실행 방법, 폴더 구조, 가정 목록, AI 사용 범위(어디까지 시켰고 어디를 직접 고쳤는지), 버린 선택지와 이유.

## 실전 프롬프트

### 요구사항 분해 (코드 생성 전 1회)

```
아래 사전과제 명세를 구현 전에 분해해라. 코드는 쓰지 마라.
출력은 다음 네 표만:
1) 화면 목록: 화면명 / 진입 경로 / 필요한 데이터 / 명세에 없는 상태(로딩, 에러, 빈 목록, 성공)
2) 엔티티: 이름 / 필드(타입, 필수 여부) / 다른 엔티티와의 관계
3) 상태 전이: 사용자 행동 -> 상태 변화 -> 서버 요청(메서드, 경로) -> 실패 시 화면
4) 검증 규칙: 입력 필드 / 규칙 / 위반 시 문구
명세에 없어서 내가 결정해야 하는 항목은 표 맨 아래 '가정' 목록으로 따로 뽑아라.
```

### 컴포넌트 스켈레톤 (파일 3개 한도)

```
규칙:
- 폴더: src/app, src/features/<도메인>/{api,hooks,components}, src/shared/{ui,lib}
- TypeScript strict, any 금지, 컴포넌트는 함수형 + named export
- 스타일은 기존 CSS 변수 토큰만 사용한다. 새 색을 만들지 마라
- 이번 응답에서는 3개 파일만 출력한다
- 설명형 주석을 쓰지 마라. 코드가 말하는 것을 주석으로 반복하면 지운다
응답 본문에 '이 파일이 가정한 것'을 파일별로 한 줄씩 적어라.
```

### 실패 경로 테스트 (Claude)

```
아래 컴포넌트와 훅의 실패 경로만 테스트해라. 성공 경로는 이미 있다.
필수 케이스: 빈 배열, 401, 500, 타임아웃(AbortError), 연속 클릭 2회, 10,000자 문자열, 한글과 기호 혼합 입력.
MSW 핸들러로 응답을 고정하고, 스냅샷 대신 화면에 보이는 문구와 버튼 disabled 상태를 검증해라.
테스트 이름은 '조건 -> 기대' 형태의 한국어 한 문장으로 쓴다.
```

### 제출 전 diff 비평 (마감 30분 전)

```
이 PR diff를 면접관 관점에서 비평해라. 가점과 감점을 각각 근거 라인과 함께 적어라.
특히 볼 것: (1) 서버 상태와 클라이언트 상태가 섞인 곳 (2) useEffect 의존성 누락, 파생 값을 state로 둔 곳
(3) 명세에 없는 동작 (4) AI가 남긴 설명형 주석과 중복 코드 (5) README에 없는 결정.
지적은 파일:라인 단위로, 고치는 방법은 한 줄로.
```
